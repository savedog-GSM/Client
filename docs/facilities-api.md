# 편의시설 경로 API 연동 안내

## 현재 상태

프론트의 스마트폰 전용 페이지는 `/facilities`입니다. 화장실·편의점 버튼을 누르면 현재 위치를 확인한 뒤 아래 API를 요청합니다.

**아래 규격은 이번 기능을 위한 신규 제안이며, 백엔드에는 아직 구현되지 않았습니다.** 백엔드 코드나 배포는 수정하지 않았습니다. 담당자가 이 규격을 확인하고 구현한 뒤 함께 연결을 검증해야 합니다.

- 실제 모드: `/facilities`. API 미구현 응답은 준비 중으로 표시하며 예시 결과로 대체하지 않습니다.
- 시연 모드: `/facilities?demo=1`. 실제 위치 권한이나 서버 요청 없이 예시 시설과 경로를 보여줍니다. 실제 보행 안내용이 아닙니다.
- 현재 프론트는 경로 조회와 텍스트 안내를 제공합니다. 지속적인 GPS 추적, 회전 시점 안내, 도착 판정, 로봇 이동 명령은 포함하지 않습니다.

## 1. 요청

`POST /api/facilities/nearest-route`

```http
Content-Type: application/json
```

```json
{
  "category": "TOILET",
  "origin": {
    "latitude": 35.14332,
    "longitude": 126.80079,
    "accuracy": 12
  }
}
```

| 필드 | 형식 | 설명 |
| --- | --- | --- |
| `category` | 문자열 | `TOILET` 또는 `CONVENIENCE_STORE` |
| `origin.latitude` | 숫자 | 현재 위도, -90~90 |
| `origin.longitude` | 숫자 | 현재 경도, -180~180 |
| `origin.accuracy` | 숫자 | 브라우저가 제공한 위치 오차, m 단위, 0 이상 |

프론트는 사용자가 버튼을 누른 뒤 최신 위치를 한 번 조회합니다. 위치 오차가 100m를 초과하거나 권한이 거부되면 요청을 보내지 않습니다. 백엔드도 좌표·종류·오차를 검증해주세요. 정확도 허용 범위를 바꾸려면 프론트와 함께 맞춰야 합니다.

시설 검색은 조회 작업입니다. 이 요청으로 로봇을 움직이거나 신고를 생성하면 안 됩니다.

## 2. 성공 응답

`200 OK`

아래 이름·주소·경로는 형식 설명용 예시입니다.

```json
{
  "facility": {
    "id": "toilet-123",
    "category": "TOILET",
    "name": "예시 공중화장실",
    "address": "시설의 실제 도로명 주소",
    "latitude": 35.14382,
    "longitude": 126.80139
  },
  "route": {
    "distanceMeters": 110,
    "durationSeconds": 120,
    "path": [
      { "latitude": 35.14332, "longitude": 126.80079 },
      { "latitude": 35.14382, "longitude": 126.80079 },
      { "latitude": 35.14382, "longitude": 126.80139 }
    ],
    "steps": [
      { "instruction": "첫 번째 모퉁이까지 보도를 따라 이동합니다.", "distanceMeters": 55 },
      { "instruction": "시설 출입구까지 보도를 따라 이동합니다.", "distanceMeters": 55 }
    ]
  }
}
```

| 필드 | 조건 |
| --- | --- |
| `facility.id` | 비어 있지 않은 문자열. 외부 공급자의 숫자 ID도 문자열로 변환 |
| `facility.category` | 요청한 종류와 동일 |
| `facility.name` | 비어 있지 않은 시설명 |
| `facility.address` | 주소 문자열. 정보가 없으면 빈 문자열 |
| `facility.latitude`, `longitude` | 시설의 실제 접근 가능한 출입구 좌표 권장 |
| `route.distanceMeters` | 해당 보행 경로의 실제 총 거리, m 단위, 0 이상 |
| `route.durationSeconds` | 해당 보행 경로의 예상 소요 시간, 초 단위, 0 이상 |
| `route.path` | 출발→도착 순서의 좌표 배열. 최소 2개. 좌표 순서 뒤바꾸지 않기 |
| `route.steps` | 순서가 있는 안내 배열. 최소 1개 |
| `steps[].instruction` | 화면 낭독기로 이해할 수 있는 비어 있지 않은 한국어 문장 |
| `steps[].distanceMeters` | 해당 구간 거리, m 단위, 0 이상 |

프론트는 종류가 다르거나 필수 경로가 빠진 응답을 표시하지 않습니다. `path`만 보내거나 거리·시간 단위를 바꾸면 연동되지 않습니다. 도보 위험 점수는 이번 응답에 넣지 않으며, 프론트도 임의로 안전 등급을 생성하지 않습니다.

## 3. 백엔드 처리 순서

1. 요청 형식과 위치 오차를 검증합니다.
2. 요청한 종류의 주변 시설 후보를 조회합니다. 화장실과 편의점은 별도 분류로 검색합니다.
3. 폐업·이용 제한 등 확인할 수 있는 조건으로 후보를 걸러냅니다. 공중화장실, 고객 전용 화장실, 운영 시간의 취급 정책은 담당자끼리 정해야 합니다.
4. 후보별로 **보행 가능한 경로**를 계산합니다. 자동차 경로를 보행 경로로 반환하지 않습니다.
5. 도달할 수 없는 후보를 제외하고, 반환 가능한 경로의 **보행 거리**가 가장 짧은 시설을 선택합니다. 직선거리가 가깝다는 이유만으로 선택하지 않습니다.
6. 지도에 그릴 좌표와 텍스트 안내를 같은 경로에서 만들어 응답합니다. 안내 단계 순서와 거리 합계를 확인합니다.

시설 검색 데이터와 보행 경로 공급자는 백엔드 담당자가 선택해야 합니다. 현재 위험 지도에 수집된 길만 사용하는 경우, 시설이 그 길과 연결되지 않으면 `PATH_NOT_FOUND`를 반환해야 합니다. 임의의 직선 연결이나 샘플 경로를 실제 응답으로 반환하면 안 됩니다.

검색 반경과 후보 수는 서버에서 제한해주세요. 초기 검색 반경 2km를 제안하지만 합의 전에는 확정값이 아닙니다. 반경을 벗어난 결과까지 무조건 반환하기보다 시설이 없는 상태를 구분해주는 편이 좋습니다.

시설을 찾았다는 사실이 시각장애인의 독립 보행이나 무장애 이용 가능 여부를 보증하지는 않습니다. 출입구·계단·횡단보도·운영 시간 정보가 불명확하면 확인된 정보와 미확인 정보를 구분해야 합니다. 추후 이런 정보를 화면에 노출하려면 응답 필드를 추가로 합의해주세요.

## 4. 오류 응답

```json
{
  "code": "FACILITY_NOT_FOUND",
  "message": "검색 범위 안에 이용 가능한 화장실이 없습니다."
}
```

| HTTP | `code` | 용도 |
| --- | --- | --- |
| 400 | `INVALID_CATEGORY` | 지원하지 않는 시설 종류 |
| 400 | `INVALID_LOCATION` | 좌표 형식·범위 오류 |
| 422 | `LOCATION_INACCURATE` | 허용 범위를 넘는 위치 오차 |
| 404 | `FACILITY_NOT_FOUND` | 범위 안에 이용 가능한 시설 없음 |
| 404 | `PATH_NOT_FOUND` | 후보는 있으나 연결 가능한 보행 경로 없음 |
| 501 | `FEATURE_NOT_READY` | 기능 미구현·비활성화 |
| 503 | `PROVIDER_UNAVAILABLE` | 시설 검색 또는 경로 공급자 장애 |

404에서는 `FACILITY_NOT_FOUND`와 `PATH_NOT_FOUND` 코드를 정확히 보내주세요. 프론트는 나머지 404를 아직 없는 API로 취급합니다. 빈 배열을 성공 응답처럼 반환하거나 0m의 가짜 경로로 대체하지 않습니다.

프론트는 API 응답을 최대 15초 기다립니다. 백엔드의 외부 공급자 제한 시간은 이보다 짧게 두고 JSON 오류 응답을 반환해주세요. 사용자가 검색을 바꾸거나 취소하면 프론트는 이전 요청을 중단하고 늦은 결과를 무시합니다.

## 5. 연결·인증

- 프론트는 기존 `VITE_API_URL`과 화면의 연결 설정을 사용합니다. 별도 서버 주소 환경변수는 추가하지 않았습니다.
- HTTPS 프론트에서 접근할 수 있도록 HTTPS API를 제공해주세요.
- CORS에서 프론트 도메인과 `POST`, `Content-Type`, 필요한 `Authorization` 헤더를 허용해야 합니다.
- 현재 프론트는 연결 설정의 관제 토큰이 있으면 `Authorization: Bearer ...`를 보냅니다. 장치 토큰은 보내지 않습니다. 일반 스마트폰 사용자에게 관제 토큰을 배포하지 않도록 사용자용 인증 정책을 정하고, 필요하면 프론트 인증 부분도 함께 변경해야 합니다.
- 외부 시설·경로 API의 서버용 비밀 키는 백엔드 환경변수로 관리합니다. 프론트에 전달하지 않습니다.
- 위치 조회 기록의 보관 여부·기간과 요청 제한은 서버에서 정해주세요. 이번 프론트는 위치를 브라우저 저장소에 저장하지 않습니다.
- 이 페이지는 로봇 센서 조회나 STOMP 연결 없이 동작합니다. WebSocket 이벤트는 이번 API에 필요하지 않습니다.

## 6. 연결 확인 목록

- [ ] 위 규격의 실제 응답으로 화장실·편의점 각각 확인
- [ ] 강·건물·담장 때문에 직선거리 순서와 보행거리 순서가 다른 경우 확인
- [ ] 시설 없음·경로 없음·공급자 장애가 각각 구분되는지 확인
- [ ] 보행 경로의 출발 위치와 실제 시설 출입구가 올바른지 확인
- [ ] HTTPS·CORS·인증과 스마트폰 위치 권한 확인
- [ ] 실제 모드가 예시 경로를 반환하지 않는지 확인
- [ ] 취소·연속 선택 시 이전 결과가 화면을 덮어쓰지 않는지 확인
- [ ] VoiceOver·TalkBack으로 버튼, 검색 상태, 결과 제목, 이동 경로 순서 확인

프론트 접근성 구현은 큰 버튼과 텍스트 경로, 상태 알림을 포함합니다. [W3C 상태 메시지 안내](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)와 [버튼 크기 안내](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)를 참고했습니다. 실제 기기 화면 낭독기 검증은 연결 확인 목록에 남겨두었습니다.
